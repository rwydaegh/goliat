\begin{abstract}
GOLIAT is an open-source Python framework for Radiofrequency Electromagnetic Field (RF-EMF) dosimetry with Sim4Life. Users define phantoms, sources, exposure cases, numerical settings, and requested outputs in hierarchical JavaScript Object Notation (JSON) files. GOLIAT supports both near-field and far-field simulation studies. The software sets up each scene, runs each job locally, across workers, or through oSPARC, extracts Specific Absorption Rate (SAR) and Absorbed Power Density (APD), and writes campaign tables and plots. GOLIAT has supported 352 near-field simulations across two child phantoms, eight frequencies, and 22 placements at each phantom--frequency pair, and 550 far-field simulations across four phantoms and 15 frequencies.
\end{abstract}

\section{Motivation and significance}

Computational \gls{rfemf} dosimetry calculates energy absorption in the body with numerical models. The main quantities are whole-body and local \gls{sar} below 6~GHz and \gls{apd} at higher frequencies~\cite{Hand2008,Hirata2021}. A study may vary the anatomical model, frequency, source position, incident direction, polarization, grid, and normalization. Together, these choices can give hundreds of \gls{fdtd} simulations.

Each simulation needs a scene, source, material assignment, grid, boundary conditions, solver settings, sensors, and extraction rules. A campaign also needs consistent names, result paths, normalization, and summary tables. Manual projects work well for a small study. However, large parameter sets need the same case setup and result collection each time.

Sim4Life (an \gls{fdtd} simulator) has anatomical models from the Virtual Population (e.g., Duke, Ella, Thelonious, and Eartha), dosimetry evaluators, a graphical interface, and a Python \gls{api}~\cite{Gosselin2014,Sim4Life}. The \gls{api} can automate one simulation. However, a study script must still list cases, name project and result files, select phases for reruns, and combine results. If one script has both the rules and scientific parameters, reviewers must read and edit program code to check or reuse the study.

GOLIAT has one workflow for study definition, scene setup, execution, extraction, and analysis. Users set scientific and numerical choices in hierarchical \gls{json} files. A base file has shared settings. Users set the phantoms, sources, exposure cases, grids, and outputs in smaller study files. GOLIAT validates the merged configuration and writes one expanded configuration for each simulation job. Users can review these files before a run and store them with the results~\cite{Sandve2013,Wilson2014}.

Near- and far-field studies use different scene rules. A near-field case places an antenna relative to an anatomical landmark and uses an input-power normalization. A far-field case defines incident fields, directions, and polarizations and uses an incident-power-density normalization. Both study types use the same job identity, execution interface, output layout, and campaign analysis.

GOLIAT uses the Sim4Life solver and evaluators. Table~\ref{tab:capabilities} lists its study-level functions. Table~\ref{tab:comparison} compares GOLIAT with three common alternatives. Because the solver is the same, the differences are only in the workflow.

\section{Software description}

\subsection{Software architecture}

Figure~\ref{fig:flowchart} shows the main components. The command-line interface loads and validates a configuration and selects a near-field or far-field study class. Both study classes use the same project manager, execution interface, status reporting, profiling, and directory layout. Exposure-specific setup and analysis classes define the geometry, source, normalization, and grouping rules.

\begin{figure*}[!ht]
  \centering
  \includegraphics[width=\textwidth]{workflow.pdf}
  \caption{GOLIAT flowchart from a hierarchical study definition to campaign tables and plots. The near- and far-field study classes share project, execution, extraction, and analysis interfaces. Dashed boxes mark external Sim4Life, model, and oSPARC resources.}
  \label{fig:flowchart}
\end{figure*}

Common settings appear once in the base configuration, including solver settings, output quantities, material rules, and paths. Source, frequency, and study choices remain in smaller derived files. The loader merges the files and validates the result before scene construction. Reviewers can compare the files and locate changes to a grid, source, phantom subset, or extraction metric. Study classes then make one job for each parameter combination, and the result tables retain the case coordinates used for comparisons.

First, setup classes set the geometry, materials, sources, grids, boundary conditions, and sensors for each job. Second, GOLIAT runs jobs with \texttt{iSolve}, the Sim4Life \gls{api}, or oSPARC. Third, extractors write common result files from Sim4Life and \gls{hdf} outputs. Finally, analysis strategies read those files without reopening every Sim4Life project.

The package keeps exposure rules separate from project and result management. Therefore, a new study type can use the common interfaces with its own setup and extraction rules.

\subsection{Software functionalities}

\subsubsection{Study definition and scene setup}

Figure~\ref{fig:configuration} depicts representative anatomical phantoms and the near- and far-field exposure paths. Near-field configurations select \gls{pifa} or \gls{ifa} models by frequency, with a material and grid setting per antenna part. For eye, cheek, trunk, or wrist cases, the antenna is placed relative to the nasion, tragus, or umbilicus with offsets and rotation sequences. Free-space cases have no phantom.

Users set the far-field source type, incident directions, polarizations, and frequencies. Spherical tessellation gives a configurable set of incident directions. A multi-sine source excites several frequencies in one simulation. The auto-induced workflow combines environmental field results, ranks candidate focus points, and extracts the selected high-exposure cases.

Both study types set solver termination, excitation, boundaries, padding, sensors, and automatic or manual grids. The default is a manual grid step per frequency: 2.5~mm up to 1450~MHz, 1.69~mm at 2140~MHz, 1.48~mm at 2450~MHz, 1.0~mm at 3.5~GHz, and 0.7~mm at 5.2 and 5.8~GHz. This gives at least 9 cells per wavelength in vitreous humor, the highest-permittivity tissue. The 5.2--5.8~GHz step is based on the grid-convergence study in Section~\ref{sec:verification} and on Laakso~\cite{Laakso2009}, who recommends 1~mm voxels only below 5~GHz. Phantom truncation is off by default. When enabled, GOLIAT keeps the head end of the phantom. The kept height scales with the cube of the grid step. Single-frequency simulations use tissue properties from the IT'IS database (v4.2) in Sim4Life. Multi-sine simulations use dispersive models fitted to the Gabriel parametric spectra of IT'IS v5.0~\cite{Gabriel1996,ITIS2024}.

\subsubsection{Execution and monitoring}

Local execution calls the Sim4Life \texttt{iSolve} executable and records its output. Split execution divides one configuration into disjoint job sets for \gls{cpu} processes or separate workstations. oSPARC execution writes solver inputs, submits batch jobs, monitors their states, retries failed submissions, and downloads the outputs~\cite{oSPARC}.

A PySide6 interface shows the active phase, completed jobs, time estimates, logs, and \gls{cpu}, memory, and \gls{gpu} use. A console mode has the same commands without the interface.

Each job has a separate Sim4Life project and result directory. GOLIAT records phase status, checks project locks and required deliverables, and retries failed saves or remote submissions. Users can rerun setup, solving, or extraction for selected jobs. A checksum identifies changes to the expanded configuration. The job record can also store the GOLIAT release, Sim4Life version, model identifiers, and material data.

\subsubsection{Extraction and analysis}

GOLIAT extracts whole-body, head, trunk, tissue-specific, and peak spatial-average \gls{sar} according to the ICNIRP guidelines and IEEE/IEC standards~\cite{ICNIRP2020,IEC627041}. GOLIAT uses a 10~g averaging mass by default and can add 1~g for the US Federal Communications Commission limits. It also extracts point-sensor fields and power balance. High-frequency studies can request \gls{apd} over a selected averaging area. Near-field results use the declared antenna input power. Far-field results use the incident power density.

Each scenario directory has the project, solver files, expanded configuration, logs, extracted results, an \gls{html} report, and metadata on timings, grid, hardware, and power balance.

Two postprocessing modules use the extracted fields. For an $N$-port device, the multi-antenna module forms one Hermitian matrix per averaging area that maps the port excitations to the \gls{apd}. Its largest eigenvalue gives the worst-case \gls{apd} under a total-power constraint. The module also has phase-only and per-port power constraints and evaluates a device's beam codebook. The formulation is from Wu et al.~\cite{Wu2024}. The measurement module reconstructs electric and magnetic fields from planar complex electric-field maps with the plane-wave spectrum, computes spatial-average power density as defined in IEC/IEEE~63195~\cite{IEC631952}, aligns measured and simulated maps, and estimates a calibration factor. The module also reads super-resolved maps, for example from the method of Yi et al.~\cite{Yi2026}.

The analysis command finds completed scenario directories and writes detailed and summary \gls{csv} files, Excel workbooks, and plots. The plots include heatmaps, line and bar charts, boxplots, cumulative distributions, and tissue rankings.

The package has commands for studies, validation, analysis, status, initialization, and parallel execution. A typical command sequence is:

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[style=goliat]
goliat validate far_field_config
goliat study far_field_config
goliat analyze far_field_config
\end{lstlisting}
\end{minipage}

The documentation has installation instructions, five tutorial notebooks, configuration references, an \gls{api} reference, cloud instructions, and troubleshooting notes~\cite{GOLIATDocs}. The Apache-2.0 package is available on PyPI~\cite{GOLIATPyPI}.

\subsection{Verification against reference solutions}
\label{sec:verification}

We ran the GOLIAT setup and extraction code in the Sim4Life~9.6 Python runner on oSPARC and compared the sphere and slab results with the analytic references in the \texttt{goliat.validation} module. For a plane wave on a homogeneous muscle sphere (radius 50~mm, 2.45~GHz), the whole-body \gls{sar} was within 1\% of the Mie solution for paddings of 5--50~mm. This test checks the incident-field normalization and the extraction of power, \gls{sar}, and mass. Without padding, the sphere touched the absorbing boundary and the whole-body \gls{sar} was 51\% too high. The default far-field padding is 20~mm, as in the environmental campaign.

Table~\ref{tab:convergence} gives a grid-convergence study for a muscle sphere (radius 25~mm, 5.8~GHz). A 1.0~mm step (7.4 cells per wavelength in muscle) underestimated the peak 10~g and 1~g \gls{sar} by 6.4\% and 5.0\% relative to a 0.35~mm grid. At the default 0.7~mm step (10.7 cells), both errors were about 2\%, which agrees with Laakso~\cite{Laakso2009}. For the 50~mm sphere at 2.45~GHz, the whole-body and 10~g \gls{sar} errors were below 2\% at the 1.48~mm default, but the 1~g \gls{sar} needed about 1.0~mm.

For a skin slab at 10 and 30~GHz, the central \gls{apd} was within $-13\%$ to $+10\%$ of the analytic transmitted power density at 10 cells per wavelength. Therefore, \gls{apd} studies at these frequencies need finer grids or a convergence check.

We also simulated a half-wave dipole over a flat phantom in the IEEE~1528 geometry, without GOLIAT's landmark-based placement. With the default grids at 835, 1900, and 2450~MHz, the peak 1~g and 10~g \gls{sar} per watt of input power were within $-0.5\%$ to $+5.2\%$ of the published values. This test checks the source, the input-power normalization, and both averaging masses. With finer grids, the 1900 and 2450~MHz values were 2--4 percentage points higher. This agreement is not a converged result, probably because of the staircased feed gap and dipole spacing.

The face intercomparison of Li et al.~\cite{Li2026} at 10 and 30~GHz reports inter-laboratory means with relative standard deviations of 16--41\%. For a dipole and a dipole array in front of the Ella head (Sim4Life~9.2), GOLIAT's \gls{apd} was 8--62\% above these means in all 24 cases, or 1.1 standard deviations on average and 2.1 at most. Li et al. used two other head models, so this comparison is only indicative. The specifications, outputs, and scripts are in the repository.

\section{Impact}

GOLIAT was developed for the European GOLIAT project. Both campaigns in Table~\ref{tab:evidence} used the same configuration, job directory, extraction, and analysis structure.

Researchers can add a phantom, frequency, incident direction, polarization, or device placement without changing the common execution and output interfaces. The same analysis code then groups results by phantom, source, frequency, exposure case, and tissue, whether the jobs ran on one workstation, across workers, or on oSPARC.

The phase logs of the 432 environmental far-field jobs give the time overhead of GOLIAT. These jobs took 54.4~h of wall time. The median job took 227~s. The median setup, solver, and extraction phases took 30, 127, and 61~s. Sim4Life operations that any workflow needs, such as voxelization and dosimetry evaluators, took 38\% of the wall time. GOLIAT's own steps took 1.8\%, a median of 9~s per job. Loading, merging, and expanding the 432-job configuration took 11~ms, and the analysis read each result record in 6.5~ms. GOLIAT was started more than once for 238 of the 432 jobs and continued from the last completed phase. The repeated work was 5.0\% of the wall time.

GOLIAT also avoids several errors of manual setup. GOLIAT places the antenna with the same landmark, offsets, and rotation sequence for every phantom and frequency, so no operator places it by hand. Material mapping, grid rules, tissue groups, and normalization are declared once and applied to every job. Result paths are derived from the case coordinates, so a result cannot be stored under the wrong phantom or placement. GOLIAT checks for missing or incomplete outputs before extraction. The power balance shows jobs where absorbed and radiated power differ from the injected power. Two jobs can be compared with a diff of their expanded configurations.

GOLIAT runs and records simulation studies, but it does not assess compliance. IEC/IEEE~62704-3 defines \gls{fdtd} procedures for mobile-phone \gls{sar} from 30~MHz to 6~GHz~\cite{IEC627043}. IEC/IEEE~63195-2 covers computational incident power density from 6 to 300~GHz~\cite{IEC631952}, and IEEE/IEC P63195-4 is the active project for absorbed power density~\cite{IEEEP631954}. A laboratory that follows these procedures can keep its placements, input power, frequencies, grid rules, averaging mass or area, and report fields in a GOLIAT configuration under change control. The laboratory remains responsible for model qualification, validation of the numerical setup, uncertainty analysis, and its quality system. The main sources of computational variability are discretization, boundary conditions, the averaging algorithm, and the anatomical and dielectric models~\cite{Hirata2026}. GOLIAT records the settings for these sources and has reference solutions (Section~\ref{sec:verification}), but it does not quantify their uncertainty for a given device.

Scene setup and solver execution need a licensed Sim4Life installation, either on Windows or through the Sim4Life Python runner on oSPARC. Continuous integration tests configuration handling, job management, analysis, and the analytic references without Sim4Life. Sim4Life version changes need \gls{api} and numerical regression checks.

\section{Conclusions}

GOLIAT uses hierarchical \gls{json} study definitions to create near- and far-field Sim4Life jobs and common analysis-ready results. The completed campaigns have 352 near-field and 550 far-field jobs with configurations, logs, and extracted results. GOLIAT does not assess compliance. A laboratory can keep a GOLIAT configuration under change control for repeatable studies. It must still qualify the models, validate the numerical setup, and analyze uncertainty. Future work could include additional study types, automated quality-control checks, and broader cloud execution.
